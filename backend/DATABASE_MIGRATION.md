# Database Migration Notes

The application now uses normalized numeric primary keys for business tables.
Old seed IDs such as `cat-rotary-screw`, `tl-1`, and `dist-1` are preserved in
the `legacy_id` column only for traceability and seed-reference mapping.

## Important

Existing tables created by the older version used `VARCHAR` primary keys. MySQL
cannot safely convert those populated primary keys to `BIGINT AUTO_INCREMENT`
through `spring.jpa.hibernate.ddl-auto=update`.

For a development database, the cleanest path is to back up any data you need,
drop the old generated tables, and let Spring Boot recreate them:

```sql
DROP TABLE IF EXISTS image_assets;
DROP TABLE IF EXISTS products;
DROP TABLE IF EXISTS product_categories;
DROP TABLE IF EXISTS industries;
DROP TABLE IF EXISTS services;
DROP TABLE IF EXISTS news_articles;
DROP TABLE IF EXISTS timeline_events;
DROP TABLE IF EXISTS job_openings;
DROP TABLE IF EXISTS leads;
DROP TABLE IF EXISTS distributors;
DROP TABLE IF EXISTS users;
DROP TABLE IF EXISTS admin_users;
DROP TABLE IF EXISTS site_content_sections;
```

Then restart the backend. The seeder will recreate normalized records.

## New ID Strategy

- `id`: numeric primary key generated by MySQL.
- `legacy_id`: old imported seed identifier, useful for debugging only.
- `slug`: public URL identifier for categories, industries, services, and news.
- `products.category_id`: real foreign key-style relation to `product_categories.id`.
- `image_assets.owner_id`: numeric owner record ID with `owner_type`.

For production, replace `ddl-auto=update` with proper migrations before launch.
